## 1. 结论摘要

**可行性：高**。纯 Python HTTP 通道已实测打通（无模拟器/无 App/无 Frida）；社区先例（ha-lixiang）验证了 60 秒级轮询 + 198 信号长期稳定；社区**没有**「理想版 TeslaMate」形态项目（确认空白）。

**系统形态（极简三件事）**：

```
┌──────────────────────── 一个容器 LiAuto-Mate ────────────────────────┐
│                                                                      │
│  Collector ──▶ SQLite(/data) ◀── Web UI (FastAPI + Jinja2/HTMX      │
│  (四态轮询状态机)     │              + ECharts + Leaflet, :8080)      │
│  SessionKeeper ──────┘            ├─ 登录面板(Playwright 内置)       │
│                                  └─ MCP :8080/mcp（Agent 只读）      │
│                                                                      │
└──────────────┬───────────────────────────────────────────────────────┘
               │ 理想同学通道（livis client，独立会话）
               ▼
   api-app.lixiang.com（VSS 实时 / 行程聚合 / 充电记录 / OTA / 保养）
   id.lixiang.com（登录与 token 交换）
   ※ 手机「理想汽车」App 完全不受影响（不同 client，§3）

   Agent（Claude/Cursor/…）──HTTP Bearer──▶ :8080/mcp（同容器同端口，§8.3）
```

## 2. 产品定义（对标 TeslaMate）

TeslaMate = 自托管数据记录器：轮询车云 API → 时序持久化 → 推导行车/充电会话/效率/电池健康 → 看板；树莓派级硬件可跑；纯 Docker。

LiAuto Mate 对标能力表：

| TeslaMate 能力 | LiAuto Mate 实现 | 数据来源 |
|---|---|---|
| 实时状态轮询 | 四态感知分档轮询（§6） | `vss/get-batch`（已实测） |
| 充电会话（SOC/功率曲线） | 状态机推导 30s 采样 + 云端记录对账 | `Battery.ChargeStatus` + 电流/电压/功率信号；`chargeRecords` |
| 行车会话（轨迹/里程/均速） | 状态机推导 + GPS 60s 面包屑 | `Location.CurrentLocationInfo`、`Carcenter.Trip.Total` |
| 效率 kWh/100km | 云端日聚合直读 + 本地推导交叉验证 | `travel/daily/aggregate` |
| 充电历史统计 | 云端镜像（4 类型聚合） | `chargeRecords/monthly*` |
| 幽灵功耗（phantom drain） | 停车期 SOC 采样（休眠后如实中断） | VSS Battery 组 |
| 电池健康（宏观） | 充电记录 + SOC 历史长期积累 | 同上 |
| OTA / 保养 / 胎压告警 | 云端镜像 + 告警页 | `ota/upgrade`、`maint/plan`、`tire/alarm` |
| 任意信号历史 | 169 路径 change-only 历史 + 趋势页 | VSS 全量 |
| ~~Grafana 看板~~ | **自建 Web UI 6 页**（§8；风格/数据层级取经 TeslaMate，§8.4） | 本地 SQLite |
| 内置 Web UI（LiveView 车辆卡片/设置页） | 概览车辆卡片 + 设置页（§8.4 取经） | 本地 |
| **MCP（Agent 查车辆信息）** | **首版内置**：`/mcp` 只读 12 工具（§8.3） | 本地 SQLite |
| MQTT / 车控 / REST | 二期可选 | — |

与 TeslaMate 的两个本质差异（设计已吸收）：
1. Tesla API 无历史数据（TeslaMate 全靠推导）；理想云端**有**行程/充电历史 → **云端历史为底、本地高频推导为精**的双轨策略，休眠漏采可回填补齐。
2. Tesla 有流式接口；理想只有拉取 → 轮询节奏是数据精度与风控/车辆状态安全的权衡核心（§6）。

## 3. 通道独立性（F1）

- 「理想同学」（`com.chehejia.livis`，client_id `40amUDKOdqQTaGDONZC1oY`）与「理想汽车」主 App 是**两个独立客户端**，独立登录会话与 token 体系。LiAuto Mate 全程 livis 通道，**不影响手机理想汽车 App**。
- **唯一 caveat**：理想账号在同一 client 内不支持长期多点在线——LiAuto Mate 重登（约 13 天一次）可能踢掉手机端「理想同学」App 的登录（若用户装了它）。缓解：一次登录吃满 13 天 cookie，绝不做无谓重登。
- 证据：11-19 实测新 device_id 登录即被接受、主 App 会话无恙（`work/spike/session.json`）；ha-lixiang README「手机 App 被登出」排障节（互踢发生在同 client 内）。

## 5. 登录与会话持久化（F2）

### 5.1 Token 生命周期（11-19 实测）

| 凭据 | 寿命 | 用途 | 刷新 |
|---|---|---|---|
| `refresh_token` | **76+ 天，每次刷新轮换** | 续期主 Bearer（**全部历史接口**） | 免密；**轮换新值必须立即持久化**（ha-lixiang 踩坑） |
| 主 Bearer | 短时效 | 行程/充电记录/OTA/保养 | refresh_token 免密续期 ✅ |
| `sso_token` cookie | **13 天** | 换 scope token 的必要条件 | ❌ 刷新不补种 → 到期需重登 |
| VSS scope token | 900s | `vss/get-batch` | cookie 在即免密现换 ✅ |

**真实边界：历史通道 76+ 天免维护；实时通道每 ~13 天一次重登。**（用户约束：短信登录、不存密码——PAKE 密码登录不采用。）

### 5.2 SessionKeeper + SessionStore

```
SessionKeeper（进程内常驻任务）
  ├─ scope token：每 15min 现换（900s 寿命提前量）
  ├─ 主 Bearer：低水位用 refresh_token 续期，轮换值事务内写库
  ├─ cookie 到期看护：T-3d 起 UI 横幅预警；到期 → NEED_LOGIN
  └─ 状态机：OK → DEGRADED(仅历史通道) → NEED_LOGIN →(网页重登)→ OK

SessionStore（SQLite 表，值 AES-256-GCM 加密）
  bearer / refresh_token / cookies / device_id / 各 token 到期时间
  ★ 断电/重启完全恢复；401/100105 结构化失效才判定过期（防「每分钟重登」风暴——ha-lixiang 真机踩坑）
```

### 5.3 Web UI 一键重登（D4，核心 UX）

登录能力内置主容器（Playwright + Chromium 随镜像），流程对用户只有三步：

```
Web UI 横幅「登录已过期 · [重新登录]」 → 登录面板：
 ① 后台自动：打开 livis 登录页 → 自动勾协议 → 自动填手机号(预配置)
    → 自动点「发送验证码」→ 滑块自动解（spike browser_login.py 已实测一次过，
    缺口检测+轨迹拖拽；风控「智能检测中」挂起 → 自动重试）
 ② 面板显示「验证码已发送至 199****8560」→ 用户在网页输入 6 位码
 ③ 后台自动填码提交 → 抓取 token/cookies → 加密入库 → 横幅消失，恢复正常
失败 → 自动重试 3 次 → 面板显示诊断截图 + [重试] 按钮
```

- 短信限频 ~2 条/10 分钟（实测）；13 天一次的重登频率，风控敞口极小。
- 兜底：CLI `liam login`（宿主机 headed 模式，spike 已验证）导入 session；手动导入 session.json（开发用）。
- 风险与退路：容器内 headless 风控敏感度需 M5 实测；不过则文档引导走宿主机 CLI 兜底（同一套核心代码）。

## 6. 采集器：车辆状态感知的四态轮询（D5，核心「度」）

### 6.1 原则

1. **绝不唤醒车辆**：采集器永不调用 `wakeup` 端点（它只属于二期车控的用户显式动作）。云端 `get-batch` 返回的是云端缓存值，不触发车端唤醒——这是 ha-lixiang 60s 轮询 + 休眠跳过的社区验证前提。
2. **车辆休眠 → 数据本来就停更**（VSS ts 不再前进），轮询拿到的只是最后已知值 → 休眠期大幅降频既省流量又降风控，零数据损失。
3. 轮询强度对齐 ha-lixiang 社区验证值（实时 60s / 配置 1h / OTA·保养 24h），不超社区已验证强度。

### 6.2 四态状态机

```
判定输入（每批次响应自带）：ConnectManager online_5g/xcu/huf、ChargeStatus、
                          挡位/速度/位置变化、VSS ts 新鲜度

┌─────────┐  挡位≠P 或 速度>0 或 位置持续移动   ┌─────────┐
│ PARKED  │ ────────────────────────────────▶ │ DRIVING │ 60s 全量批 + 10s 定位微轮询
│ _AWAKE  │ ◀──────────────────────────────── │         │（仅 3–5 路径，见下）
└────┬────┘   静止+P 持续 5min（滞回防抖）      └─────────┘
     │ online
     ▼
┌─────────┐  ChargeStatus ∈ 充电态（快/慢/预约执行）
│ CHARGING│ 30s 全量批（充电采样：SOC/功率/电流/电压/温度）
└─────────┘
     │ 充电结束 → PARKED_AWAKE
┌─────────┐  连续 2 次探测 offline 或 ts 停更（防单次抖动）
│ ASLEEP  │ 60s 轻探测（仅 ConnectStatus 等 3–5 路径，对齐 ha-lixiang 强度；
│ (休眠)  │  可配 5–15min 更保守）→ 探测到苏醒立即恢复全量
└─────────┘  保留上一帧 + UI 标注「休眠中，数据截至 xx:xx」
```

- **PARKED_AWAKE**（如哨兵开启、人在车内）：60s 全量批 —— 幽灵功耗数据来源。
- **行驶态双轨**（v1.2 新增）：全量批 60s 不变；叠加**定位微轮询 10s**（可配 5–30s，`LIAM_DRIVE_LOC_INTERVAL`），每批仅带 3–5 条路径（`CurrentLocationInfo` + 挡位/动力 + `Trip.Total`）。
  - **时速免费获得**：位置 payload 自带 `spd/dir`（{lat, lon, spd, dir, alt, hdop, sat, utc}）——UI 时速/航向随 10s 采样刷新，无需额外信号。
  - **单程里程精度**：`Trip.Total` 10s 增量 → 里程累计到 ~300m 级（60s 采样只有公里级）。
  - 风控预算：行驶中请求率 ≈ 7 次/min（6 微批 + 1 全量批），与前台 App 车辆页同量级；微批仅 3–5 路径，单次负载远小于全量批；**仅行驶态启用**（典型日 1–2h）。ha-lixiang 的 30s 下限针对 198 路径全量批，不可直接类比；下限 5s 在设置页标注风控提示。
  - 轨迹粒度（诚实边界）：10s ≈ 城市 60km/h 每 ~170m / 高速 120km/h 每 ~330m 一个点——路口转弯会被平滑（展示时服务端 Douglas-Peucker 抽稀，原始点全量保留）。**云端无轨迹数据可回填**：travel 接口实测只回月/日/全量聚合（ha-lixiang 已验证），无 GPS 折线——轨迹唯一来源是本地采样，这是 10s 微轮询的必要性依据。
- 苏醒检测盲区 ≤1 个探测间隔；行程/充电开头若漏采，由云端历史（§4.2）回补——这是双轨策略的直接收益。
- 车辆自然苏醒时机 = 车主用车 / 预约充电开始 / 哨兵事件，采集器从不主动制造。

### 6.3 分档总表

| 档 | 频率 | 内容 |
|---|---|---|
| T1 实时（awake 态） | 60s（可配 30–3600s） | ~80 核心路径全量批 |
| T1++ 行驶定位 | **10s**（可配 5–30s） | **仅 3–5 路径微批**：位置（含 spd/dir）+ 挡位/动力 + Trip.Total；行驶态专用 |
| T1+ 充电激活 | 30s | 充电采样入 `charge_samples` |
| T2 配置 | 1h | 座椅/车设/场景等低频路径 |
| T3 慢档 | 24h | OTA / 保养计划 / 胎压告警 |
| T4 云端历史 | 每日 04:00 | travel daily/monthly、chargeRecords 幂等同步；**执行 retention 清理** |
| T0 休眠探测 | 60s 轻探测（可配 5–15min） | 仅 ConnectStatus 等 3–5 路径 |

错误退避：连续失败指数退避（1→2→4→8…min，封顶 30min）；401/风控码 → 停轮询 + NEED_LOGIN/告警，绝不风暴重试。

## 7. 存储：SQLite（WAL）单文件

v1.0 的 Postgres/TimescaleDB 随 Grafana 一并移除：单进程单写者、自建 UI 直接 SQL 查询、单卷备份 = 拷一个文件。

**容量实测估算**（重使用场景：日驶 2h + 日充 2h，v1.2 轮询档位）：

| 表 | 写入条件 | 日增 | 年增（行） | 年增（体积） |
|---|---|---|---|---|
| `state_history` | change-only；行驶/充电期 ~10–25 变化值/分钟，静止期 ~2/min | ~6k | ~2.2M | ~330MB |
| `positions` | 行驶态 10s 微轮询（720/h × 2h） | ~1.4k | ~0.5M | ~45MB |
| `charge_samples` | 充电态 30s（120/h × 2h） | ~240 | ~90k | ~7MB |
| 会话/云端镜像/collector_log | 小 | ~1k | ~0.4M | ~20MB |
| **合计** | | **~9k 行/日** | **~3.2M 行/年** | **~400MB/年（含索引）** |

SQLite 在此规模**无性能压力**：千万行级、单写者 WAL、全部查询走索引时间窗扫描（趋势页 30d × 高频路径 ≈ 45k 行索引扫描，毫秒级）。「量大」的真实风险（库体积无限增长）用**保留策略**控制，而不是换数据库：

| 数据 | 保留策略 |
|---|---|
| `state_history`（原始 change） | **默认 90 天**（`LIAM_RETENTION_DAYS` 可配），到期由 T4 任务删除——长期有价值的数据已固化进会话聚合表与云端镜像表 |
| `positions` | 随 `drive_sessions` **永久保留**（~45MB/年，无需清理）；展示时服务端 Douglas-Peucker 抽稀 |
| `charge_samples` | 随 `charge_sessions` 永久保留（~7MB/年） |
| 会话/云端镜像 | 永久保留（量小） |
| 空间回收 | 建库即开 `auto_vacuum=INCREMENTAL`，T4 清理后执行 `incremental_vacuum` |

| 表 | 说明 |
|---|---|
| `state_latest` | 169 路径最新值（jsonb 值 + 车端 ts） |
| `state_history` | change-only，索引 (path, ts)，来源标注 vss/cloud/derived |
| `positions` | 行驶态 GPS 面包屑（ts, lat, lon, spd, dir, alt, drive_session_id），索引 (drive_session_id, ts) |
| `charge_samples` | 充电态 30s 采样（soc, power_kw, current, voltage） |
| `charge_sessions` / `drive_sessions` | 推导会话 + 云端对账字段（余量/偏差标记）+ 起止 position 引用（TeslaMate `drives` 同构） |
| `states` | **车辆状态时间线**（driving/charging/parked_awake/asleep/offline，起止 ts）——TeslaMate `states` 表同构；四态状态机每次变迁即写，一条连续历史 |
| `geofences` | **用户命名地点**（名称/lat/lon/半径，默认 100m，如「家」「公司」）——TeslaMate 同名表；会话起止点命中 geofence 即自动命名（「家 → 公司」） |
| `addresses` | 可选：起止点反向地理编码缓存（在线 Nominatim，**默认关闭**——geofence 已覆盖核心 UX，避免外部依赖） |
| `travel_daily` / `charge_records_cloud` / `ota_updates` / `maintenance_plan` | 云端镜像（幂等 upsert，支持历史回填） |
| `session_store` | 凭据（AES-256-GCM 加密）+ 到期时间 |
| `collector_log` | 每批次健康（状态/延迟/路径数/错误）→ 系统页自监控 |

**Postgres 迁移触发条件**（写死判据，满足才迁，避免过早优化）：单表 >5000 万行（≈ 15 年用量）或库 >10GB（关闭 retention 的极端用法）或趋势页 P95 查询 >500ms。表结构保持 vanilla SQL（不用 SQLite 专有特性），迁移 = 导出/导入 + 改 DSN。

#### 8.1.1 地图瓦片与坐标（v1.4 细化）

**坐标事实（决定性）**：理想 VSS 上报的是 **WGS-84 原始 GPS 坐标**（ha-lixiang 实测结论：未经国测局偏移；`device_tracker.py` 注释）。而高德/腾讯底图是 **GCJ-02（火星坐标）**，OSM 是 WGS-84。

**设计原则：库内永远存 WGS-84 原始值，坐标转换只在展示层做**（`wgs84→gcj02`，公开算法 ~20 行，精度损失 1–2m 可忽略）。这样换任何底图都不动数据层，导出的轨迹可直接喂 Google Earth（同为 WGS-84）。

| 瓦片源 | key/费用 | 坐标 | 国内速度 | 备注 |
|---|---|---|---|---|
| **高德栅格瓦片（无 key 退路）** | 免 key、无配额概念 | 需 GCJ 转换 | 快 | **v1.5 拍板**：`LIAM_AMAP_KEY` 未设置时自动用此模式；`webst0{1-4}.is.autonavi.com` 栅格瓦片 |
| **高德 JS API（有 key 默认）** | 个人认证 ~15 万次/月免费（用户已有 key） | 需 GCJ 转换 | 快 | **v1.5 拍板**：`LIAM_AMAP_KEY` 设置时自动用此模式；有审图号最合规；自用量远低于配额 |
| OSM（备选） | 完全免费 | WGS-84 直用 | 不稳定 | `LIAM_MAP_PROVIDER=osm` 强制指定时才用 |

配置（v1.5 已拍板：高德为选定方案）：`LIAM_AMAP_KEY` 设置 → 自动用**高德 JS API（官方，有审图号，最合规）**；未设置 → 自动退回**高德栅格瓦片直连**（免 key）。两条路线同一套坐标转换与前端代码，切换零成本。OSM 保留为 `LIAM_MAP_PROVIDER=osm` 备选。

## 9. Docker 部署（D3：单容器）

```yaml
# docker-compose.yml（全部内容）
services:
  liauto-mate:
    image: ghcr.io/<owner>/liauto-mate:latest   # python:3.12-slim + Playwright/Chromium ≈ 1.5GB（一次性）
    container_name: liauto-mate
    ports: ["8080:8080"]
    volumes: ["liauto-mate-data:/data"]          # SQLite + 加密凭据，全部状态在此
    environment:
      LIAM_UI_PASSWORD: "${LIAM_UI_PASSWORD}"   # 必填
      LIAM_PHONE: "199****8560"                  # 可选；也可首启向导里填
      LIAM_MCP_TOKEN: "${LIAM_MCP_TOKEN}"        # 可选；设置才启用 /mcp（§8.3）
    restart: unless-stopped
volumes:
  liauto-mate-data: {}
```

- **单容器 / 单卷 / 单端口**：升级 = 换镜像标签；备份 = 拷卷；迁移 = 拷卷到新机器。
- 镜像内含 Playwright+Chromium（登录用，约 +1.3GB），换来「重登永远可用、无第二容器」的运维简洁——这是 D3/D4 的直接取舍。
- 首启向导：设密码 → 填手机号 → 走登录面板 → 完成采集。
- 可选拆分（文档注明，不做）：登录拆独立 profile 容器共享卷，主镜像可瘦身到 ~250MB；仅当镜像体积成为实际痛点时再拆。

## 13. 开工注意事项（v1.6，M0 前最后清单）

### 13.1 开工纪律（红线）

- **CI/测试永不打真实 API**：单测全部 fixture/录制回放；真实链路只走手动 smoke 脚本，且在 .env 配置下显式开启。
- **新仓库第一天 `.gitignore` 封死凭据**：`session.json`、`*.db`、`.env`、`data/` 绝不入库；开源前再做一次 secrets 全量扫描（gitleaks）。
- **单账号单车**：开发期也绝不并发/压测云端；登录相关测试按短信限频（~2 条/10 分钟）排期，能不测就不测。
- **配方钉住**：8.25.4 / iPad UA / iOS 语义签名不做版本实验；盯 ha-lixiang 上游 commit 作为免费前哨（它先遇到漂移）。

### 13.2 开发期实测标定项（写状态机之前先观察）

- **观察期先行**：M1 写状态机前，先用 spike 代码直采 48h 入库，拿本车真实休眠/苏醒模式（每辆车阈值不同），再定滞回参数——勿拍脑袋。
- **ChargeStatus 枚举映射未标定**：实车只观察到静止值 15；充电中/插枪/预约执行的枚举值需在 M2 观测一次完整充电来标定。`CLTC/WLTCChargePower` 单位（kW vs W）同批确认。
- **时间戳两种结构**：VSS ts 为毫秒（浮点）；`VehInfo.CarCenter.*` 组是嵌套对象自带 `timestamp` 字段——解析层按 03 注册表 per-path 处理；存储统一 UTC 毫秒，展示转 Asia/Shanghai。

### 13.3 工程坑

- **Playwright/Chromium 的 linux/arm64 镜像**（ARM NAS 部署场景）：M5 验证项；镜像用 buildx 出 multi-arch（arm64 + x86）。
- **时区**：全程 UTC 存储 + 展示层转换；「自然日」边界用本地时区日（T4 的 04:00 同理）。
- **开源脱敏（若将来开源）**：README 带非官方/风险自担声明（同 ha-lixiang 做法）；MIT 移植注明出处；不携带任何个人数据、坐标样本、密钥。

### 13.4 开发期自然节点

- spike 会话的 sso cookie（13 天）约 **2026-12-02 到期**——正好落在 M2 期间，把 D4 网页重登流程当真实场景实测一次（坏事变好事）。
- refresh_token（76+ 天）期间无需理会。
